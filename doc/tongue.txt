1. INTRODUCTION                                          *tongue-introduction*

tongue.nvim forces English in Normal mode and restores the input method you
were last typing with when you enter Insert or Terminal-insert mode.

It exists because the usual approach does not work for external Vietnamese
IMEs. GoTiengViet, EVKey, OpenKey and GoNhanh are processes layered on top of
`com.apple.keylayout.ABC`, so "Vietnamese" and "English" are the SAME macOS
input source. A plugin that switches input-source IDs cannot express the
difference at all. tongue.nvim drives the `tongue` CLI, which moves both the
layout and the IME process.

Three design properties are load-bearing:

- Nothing blocks the UI. A backend read costs 40-50ms, and the obvious
  implementation pays that on every exit from Insert mode.
- Mode tracking uses |ModeChanged|, not |InsertLeave|. `i_CTRL-C` leaves
  Insert mode WITHOUT firing InsertLeave (see |i_CTRL-C|), which would strand
  you in Normal mode with the IME still on, indefinitely.
- A process is spawned only when it can change something. Leaving Insert reads
  the machine, because a switch made by hand can only be learned from it;
  entering Insert does not, because the plugin forced English on the way out
  and knows it landed. See |tongue-behaviour|.

2. REQUIREMENTS                                          *tongue-requirements*

Neovim 0.10 or newer -- |vim.system()| is the only command runner that both
separates stderr from stdout and supports a timeout, and both matter here.

A backend on $PATH. Auto-detection takes the first one it finds, in order:

    macOS     tongue          https://github.com/xom11/tongue
              macism          https://github.com/laishulu/macism
              im-select       https://github.com/daipeihust/im-select
    Linux     fcitx5-remote   (ships with fcitx5)
              ibus            (ships with ibus -- the GNOME default)
              xkb-switch      https://github.com/grwlf/xkb-switch
              im-select.exe   (WSL: the Windows IME is the visible one)
    Windows   im-select.exe
    other     supply your own, see |tongue-backends|

Note: the `tongue` crate on crates.io is an unrelated program. Do not install
it with `cargo install tongue`; use the repository above.

The order is a promise. On macOS, macism and im-select read and write
input-source IDs, which is the weaker lever: with an external IME, "vi" and
"en" are the SAME input source and they cannot tell them apart. On Linux, an
input-method framework (fcitx5, ibus) outranks xkb-switch for the same reason
-- xkb-switch moves the keyboard layout and cannot see that a framework is
running at all. The weaker backends are still worth detecting -- the OS's own
Vietnamese, Japanese and Chinese input sources are served fine by them -- and
|tongue-health| says so out loud when you land on one.

3. SETUP                                                        *tongue-setup*

                                                              *tongue.setup()*
>lua
    require("tongue").setup({
      backend = nil,    -- preset name or table, see |tongue-backends|
      english = nil,    -- override the resolved backend's English token
      notify  = true,   -- warn on backend failure (throttled, 30s per kind)
      timeout = 2000,   -- per-command deadline in milliseconds, minimum 100
      verify  = false,  -- read the machine before every switch
    })
<
`backend` accepts a preset name as well as a table: >lua

    require("tongue").setup({ backend = "macism" })
    require("tongue").setup({ backend = "im-select" })  -- `im_select` too
<
`english` applies to whatever backend was resolved, auto-detected too, and
is validated against it. The common case needs nothing else: >lua

    -- macism is installed; this machine types on US, not ABC
    require("tongue").setup({ english = "com.apple.keylayout.US" })
<
Get `english` right. Measured on macism 3.1.1: an input source that does not
exist on this machine makes it print "Input source ... does not exist!" on
STDOUT and exit 0 -- a failure with no exit code to read. The plugin catches
that (a `set` that prints anything is not believed), and so does
|tongue-health|, which tries the switch rather than only reading -- run it
while your other input source is active. See |tongue-set-probe|.

`timeout` is validated rather than silently defaulted. Below 100ms the
deadline fires before a healthy backend can answer, which is indistinguishable
from a broken backend; a non-number, or 0, or a negative value, each break the
deadline in their own way. All of them are reported as config bugs.

The deadline is enforced by the plugin, not merely passed to |vim.system()|.
That matters when writing a backend: vim.system's own timeout kills the
process it started but still waits for the stdout pipe to close, and a shell
wrapper running its work in a subprocess leaves a grandchild holding that
pipe. Measured: a wrapper forking `sleep 5` with timeout=200 called back after
5016ms; the same script using `exec` came back at 202ms.

setup() is required. Nothing happens on `require` alone.

With no supported backend, and in SSH sessions, the plugin stays inert. That
is deliberate, not a failure: over SSH the input method that matters is the
client's.

`notify = false` silences runtime warnings only. A malformed `backend`,
`english` or `timeout` is always reported, because a config bug that silently
disables the plugin is the exact failure this plugin exists to prevent. Being
inert is not a config bug and stays silent.

4. BEHAVIOUR                                                *tongue-behaviour*

    starting Neovim         read once, remember it, force English
    entering Insert/Term    restore the remembered token
    leaving Insert          force English -- including <C-c>, macros, :normal!
    manual switch in Insert noticed on the way out, restored next time
    completion, i_CTRL-O    nothing; these never leave Insert
    FocusGained in Normal   re-read the machine, re-assert English

All backend calls are asynchronous and single-flight: a burst of 60 mode
changes costs one process.

                                                            *tongue-fast-path*
Most boundaries cost nothing at all. Leaving Insert always reads the machine
-- a switch you made by hand can only be learned from it -- but entering
Insert does not: the plugin forced English on the way out and knows it landed,
so it issues the restore directly instead of asking a question it holds the
answer to. Measured against the test fixture, an Insert round trip went from
four processes to three, and a session that never leaves English from two to
one. The restore also lands one whole read (40-50ms with `tongue`) sooner.

What that gives up is one case: an input method changed by hand IN NORMAL
MODE, with no focus event to notice it. That change now survives into Insert
instead of being overwritten. `verify = true` buys the old
read-before-every-switch behaviour back.

==============================================================================
5. COMMANDS                                                  *tongue-commands*

                                                                     *:Tongue*
One command, one subcommand, with completion:

    :Tongue                 same as :Tongue status
    :Tongue status          what the plugin is doing, spawning nothing
    :Tongue toggle          stop / start acting
    :Tongue enable          start acting; re-learns rather than trusting a
                            cache that may be stale
    :Tongue disable         stop acting; the input method is left where it is
    :Tongue sync            re-read the machine and re-assert

`:Tongue status` is instant and says what the plugin INTENDS. |tongue-health|
spawns the backend and says whether it WORKS. Reach for the first when the
behaviour surprises you, the second when nothing happens at all.

6. LUA API                                                        *tongue-api*

                                                             *tongue.enable()*
                                                            *tongue.disable()*
                                                             *tongue.toggle()*
                                                               *tongue.sync()*
>lua
    require("tongue").enable()   --> boolean: false if there is no backend
    require("tongue").disable()
    require("tongue").toggle()   --> boolean: the state it left behind
    require("tongue").sync()
<
`disable()` leaves the input method exactly where it is. Switching it on the
way out would be a surprise in one direction or the other, and your own hotkey
is one keystroke away.

`sync()` is for an input method changed outside Neovim without Neovim ever
losing focus -- the one case |tongue-fast-path| cannot see by itself.

                                                              *tongue.token()*
                                                             *tongue.layout()*
>lua
    require("tongue").token()    --> "vi", or nil when inert/disabled
    require("tongue").layout()   --> the token Insert mode will restore
<
`token()` is the INTENT, not a reading: it is right the instant the mode
changes, some 200ms before the machine gets there. That is what a statusline
wants; see |tongue-statusline|.

                                                             *tongue.status()*
Returns a table describing the resolved backend and the current state. Used by
|tongue-health| and by `:Tongue status`; also what to paste into a bug report.
Fields: `enabled`, `attached`, `misconfigured`, `reason`, `backend` (a copy),
`last_layout`, `inserting`, `busy`, `observe`, `applied`, `timeout`, `verify`.

7. STATUSLINE                                              *tongue-statusline*

                                                         *tongue.statusline()*
>lua
    require("lualine").setup({
      sections = { lualine_x = { require("tongue").statusline } },
    })
<
It returns the empty string whenever there is nothing worth saying, which is
most of the time. Three optional keys: >lua

    require("tongue").statusline({
      format   = " %s",  -- anything that is not English  (default "%s")
      english  = "",     -- while English is in force     (default "")
      inactive = "",     -- while inert or disabled       (default "")
    })
<
                                                               *TongueChanged*
A |User| autocommand event, fired only when |tongue.token()| or
|tongue.layout()| can have changed -- never on completion churn, never on the
59 coalesced mode changes of a burst. So a component can refresh on the event
rather than polling: >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "TongueChanged",
      callback = function(ev)
        -- ev.data = { token = "vi", layout = "vi", inserting = true }
        vim.cmd.redrawstatus()
      end,
    })
<
`ev.data.token` and `ev.data.layout` are BOTH nil while the plugin is inert or
disabled, and that firing is the point: it is what tells a component to clear
itself after `:Tongue disable`. Handle nil, or use |tongue.statusline()|,
which does it for you.

The same surface is the hook for what the plugin deliberately does not do
itself -- turning it off inside a fuzzy-finder prompt, for instance, with
`disable()` on FileType and `enable()` on BufLeave.

8. CUSTOM BACKENDS                                           *tongue-backends*

A backend is a table: >lua

    {
      english = "1033",              -- token forced in Normal mode (required)
      get     = { "im-select.exe" }, -- argv, prints current token  (required)
      set     = { "im-select.exe" }, -- argv, token appended        (required)
      unknown = nil,                  -- token meaning "unrecognised"
      tokens  = nil,                  -- allow-list, nil = any single word
      note    = nil,                  -- shown by |tongue-health|, no effect
    }
<
`get` must print exactly one whitespace-free token. Output with interior
whitespace is REJECTED rather than cleaned up: readers that merge stderr into
stdout turn a stray warning line into one plausible-looking token, which then
gets stored and replayed as an argument forever.

`set` must be SILENT on success. Anything it writes to stdout counts as
failure, whatever the exit code says -- `tongue en` and `fcitx5-remote -s`
print nothing, while macism 3.1.1 reports a nonexistent input source exactly
that way and still exits 0. A backend with no exit code worth reading leaves
its output as the only evidence there is.

A `set` that reports failure is CONFIRMED against the machine before it is
believed: "said it failed" and "failed" are not the same thing. IBus
1.5.34-rc2 exits 1 while the engine changes, because `ibus engine` also shells
out to setxkbmap. One read settles it, and costs nothing on a backend that
does not lie: the confirmation happens only when a `set` reports failure.

`unknown` is what the backend prints when it does not recognise the live
state. It is NOT treated as English: a shrug is not evidence, so the plugin
neither learns a layout from it nor concludes "already English" and skips the
switch. Forcing English is what should happen there, and it does.

If `tokens` is given it must contain `english`.

Presets: `require("tongue.presets")` -- `.tongue`, `.macism`, `.im_select`,
`.im_select_exe`, `.fcitx5`, `.ibus`, `.xkb_switch`.

What has been run: every one of the seven backends, against its real binary.

tongue          verified end to end on macOS 26.5.1 arm64, Neovim 0.12.4,
                through auto-detection rather than an explicit `backend`. The
                contract is exact: `tongue` prints the mode and exits 0,
                `tongue <mode>` is silent and exits 0, an unknown mode exits 2
                with a message on stderr.

macism          verified end to end on macOS 26.5.1, Neovim 0.12.4, macism
                3.1.1, against the real macOS Vietnamese IM. Picked when
                tongue is absent; outranked by tongue when both are present.
                Reads cost ~22ms (tongue: ~40-50ms, it moves an IME too).
im-select.exe   driven end to end on Windows 11 ARM64, Neovim 0.12.4, as a
                hand-written backend. Auto-detection verified there too: uname
                says Windows_NT, it resolves im-select.exe, and `english`,
                `backend = "im-select.exe"` and a rejected malformed `english`
                all behave as documented. The pure specs (mode, sanitize,
                backend) run on a real Windows runner in CI; the rest of the
                suite cannot, because tests/fixtures/fake-im is a POSIX shell
                script. That is the harness, not the plugin.
im-select       driven end to end on macOS 26.5.1 arm64, Neovim 0.12.4,
                im-select 1.0.1, against the real macOS Vietnamese input
                method. `im-select` prints the source and exits 0; `im-select
                <id>` is silent and exits 0 for a real source and EXITS 1 for
                one that does not exist -- the only input-source backend that
                reports a bad token at all. On the same machine with `tongue`
                installed too, auto-detection still picks `tongue`.
fcitx5          driven end to end on Ubuntu 26.04 arm64, Neovim 0.11.6, fcitx5
                5.1.19 + fcitx5-unikey, in a headless sway 1.11 session. Fits
                the contract -- but `-s` exits 0 in SILENCE for a name not in
                your group, changing nothing, and `-n` prints nothing at all
                without a focused input context. See |tongue-health|.
ibus            driven end to end on the same machine, IBus 1.5.34-rc2 with
                ibus-unikey. Works, but `ibus engine <name>` EXITS 1 while
                succeeding: it also runs setxkbmap, which fails without a
                usable X display. Every restore is therefore reported as a
                failed command, and the fast path never engages.
xkb-switch      driven end to end on the same machine, xkb-switch 2.1.0 with a
                us,vn layout pair. Fits the contract exactly, and is the only
                one of the three that reports a bad token (exit 2, with a
                message). Still moves the X keyboard layout only, hence its
                note and its place last in the Linux chain.

Every OS chain, Linux and Windows included, is exercised from a Mac:
tests/backend_spec.lua drives resolve() through an injected prober rather than
asking the real machine. That tests the CHAIN, not the binaries.

9. HEALTH                                                      *tongue-health*

>vim
    :checkhealth tongue
<
Reports which backend was resolved and why, whether it is currently disabled,
resolves both the `get` and the `set` binary to full paths, runs one real read
within the configured `timeout`, and flags a backend that writes to stderr on
success or answers with something outside its declared token set -- which is
what a name collision looks like from here.

                                                            *tongue-set-probe*
It also TRIES THE SWITCH, which is the only way to catch a `set` that lies --
fcitx5 with a name outside your group, macism with an input source that does
not exist. Nothing a running plugin reads can see that. The probe only ever
switches TOWARDS `english`, and only from somewhere else, then puts the
machine back: >

    ok    reads back "unikey"
    ok    `set` works: "unikey" -> "keyboard-us"
<
Already in English there is nothing to prove, and it says so -- switch to your
other input method and run it again. If it fails to restore, it fails towards
the state Normal mode wants anyway.

A CONFIG BUG is reported as an error, not as the same neutral note as "there
is no IME tool on this machine". The distinction matters: the startup
notification has long scrolled away by the time anyone runs this.

It also prints the resolved backend's `note` if it has one. That is where you
find out that macism, im-select or xkb-switch cannot see an external IME: the
plugin looks identical from the outside whether it is enforcing English or
merely reselecting an input source that was never what made you type
Vietnamese.

10. LIMITATIONS                                           *tongue-limitations*

- Command-line mode counts as Normal. Correct for `:`, arguably wrong for `/`;
  the mode string cannot distinguish them.

- The SSH guard reads the environment, and environments lie. It fires on
  $SSH_TTY, $SSH_CONNECTION or $SSH_CLIENT -- all three, because tmux's
  `update-environment` refreshes SSH_CONNECTION on attach and never SSH_TTY,
  so `ssh box` -> `tmux attach` -> `nvim` arrives with only the former. A tmux
  server first started inside an SSH session keeps a stale value for as long
  as it lives, leaving the plugin inert locally; |tongue-health| names the
  variable that fired so you can see that is what happened. Windows OpenSSH
  sets none of the three (measured on Windows 11 ARM64), so Neovim run over
  SSH INTO Windows does auto-detect im-select.exe -- which needs a foreground
  window and answers "0" without one. That "0" is declared as the backend's
  no-idea sentinel, so it is no longer mistaken for a layout to restore, but
  nothing useful happens.

- A switch takes as long as the backend takes (~200ms for `tongue`, which
  starts and stops an IME process). The window after leaving Insert where the
  switch has not landed cannot be closed from inside an editor plugin.

- A manual switch made while one of our commands is already in flight, and
  followed immediately by leaving Insert, is missed. It corrects itself on the
  next Insert session.

- An input method changed by hand in NORMAL mode survives into Insert rather
  than being overwritten, because entering Insert no longer re-reads the
  machine. Set `verify = true` for the old behaviour. See |tongue-fast-path|.

- The layout is remembered per Neovim, not per buffer: one token, whichever
  buffer you were in when you chose it.
